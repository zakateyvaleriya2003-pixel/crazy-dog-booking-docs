# Архитектура системы

## Общая схема

В исходном документе указан стек Django, SQLite и Bootstrap. Для учебного прототипа принимается серверное веб-приложение: браузер отправляет запросы Django, сервер проверяет права и бизнес-правила, обращается к базе через ORM и формирует HTML-страницы. Bootstrap используется для адаптивного интерфейса.

## Логические модули

- Учётные записи: вход, выход и роли клиента, кинолога и администратора.
- Питомцы: карточки собак и связь с владельцем.
- Расписание: занятия, интервалы времени, залы, кинологи и вместимость.
- Бронирование: запись питомца, проверка доступности места, отмена и история статусов.

## Основные сущности

| Сущность | Основные атрибуты и связи |
|---|---|
| User | Идентификатор, имя, контакт, роль |
| Pet | Идентификатор, владелец User, кличка (1–60 символов после удаления крайних пробелов), порода, необязательный возраст в полных месяцах (целое ≥ 0), особенности |
| Trainer | Идентификатор, учётная запись User, профиль кинолога |
| Hall | Идентификатор, название зала |
| Session | Идентификатор, вид занятия, начало, окончание, кинолог Trainer, зал Hall, вместимость |
| Booking | Идентификатор, питомец Pet, занятие Session, статус, время создания |

Число свободных мест вычисляется как вместимость минус число подтверждённых бронирований. Копия этого числа в карточке клиента не является источником истины. Уникальность активной пары Pet–Session и проверка вместимости должны обеспечиваться согласованной серверной операцией.

## Ограничения учебного прототипа

SQLite принимается как исходный выбор для учебной версии. Реализацию одновременного бронирования необходимо проверить отдельно: раздельные операции «прочитать остаток» и «создать запись» не обеспечивают требование FR-05. В этой работе задаются архитектурное правило и тест TC-04; готовое решение конкурентного доступа не заявляется.

При изменении расписания сервер повторно проверяет пересечение интервалов одного кинолога или зала. Вопрос изменения уже забронированного занятия требует отдельного согласования и не включается в базовый сценарий создания занятия.

## Проверка доступа

Сервер связывает запись с владельцем через Booking → Pet → User. Кинолог получает данные через назначение Trainer → Session. Одного скрытия кнопок или фильтра в браузере недостаточно. В публичный репозиторий не помещаются рабочая база данных, пароли, ключи и реальные сведения клиентов.

## Привязка требований к модулям

| Модуль | Требования | Проектные классы |
|---|---|---|
| Учётные записи | FR-01 | User, Trainer; связи с Pet и Session |
| Питомцы | FR-02 | Pet, User |
| Расписание | FR-03, FR-07 | Session, Hall, Trainer |
| Бронирование | FR-04–FR-06, FR-08–FR-10 | Booking, Pet, Session; доступ через User и Trainer |

Список участников (FR-08) формируется по Booking и назначению Trainer–Session; интерфейс находится в расписании кинолога, а отбор записей относится к модулю бронирования.

## Уточнения после ревью

Поле Pet.age_months хранит необязательный возраст в полных месяцах; формат одинаков в требованиях, UC-05 и диаграмме классов. При сохранении проверяются владелец, кличка и возраст.

Фильтры по дате начала занятия и виду занятия образуют совместное условие «И». Дата интерпретируется в настроенном часовом поясе центра. Пустой набор отображается как «Занятия не найдены», сброс снимает оба ограничения.

Состояния формы «Сохранение» и «Результат не подтверждён» не записываются в Booking.status. Если ответ потерян после сохранения, данные перечитываются через «Мои записи». При повторном запросе действует серверное правило единственной активной пары Pet–Session. Диаграмма и TC-10 описывают как потерю запроса до сохранения, так и потерю ответа после сохранения; наличие готового механизма в приложении не заявляется.

Допустимые переходы Booking.status: «Подтверждена» → «Отменена» по FR-06 и «Подтверждена» → «Завершена» по FR-10. Завершение выполняет администратор после окончания Session; из «Отменена» переход в «Завершена» запрещён. Повтор завершения не изменяет состояние.
